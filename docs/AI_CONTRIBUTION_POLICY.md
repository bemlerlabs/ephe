# AI contribution policy

This repository is written with AI tools in drafting and in review, and says so. This
document is the policy that makes the claim worth something: what a contribution must
disclose, what is rejected, and which check enforces each rule.

It applies to every change to this repository. The bar is the same whether a human, an
assistant, or both wrote the change — authorship does not change the bar, it changes only
what has to be disclosed.

## Disclosure

- **At release level.** Release notes state that the version was produced with tooling
  (see `.github/RELEASE_PROCESS.md`). Individual commits carry no stamp: the release note
  is one line a reader sees, while a per-commit trailer is a claim a reader skips.
- **At pull-request level.** A pull request states in one line whether an AI tool drafted
  or rewrote a substantial part of the change. One sentence in the description is enough;
  the reviewer needs to know what to check, not a per-file census.
- **No tool signatures in the tree.** No "generated by" marker, no tool name in a comment,
  docstring, PR-body template block, or commit body, no bot co-author trailer. Disclosure
  lives where a reader looks for it — the PR and the release note, the two surfaces a
  reader already opens.

Release-level rather than commit-level because the honest claim is that a responsible
human understood the change, which the CI gates and the review gate below already hold. A
commit stamp adds no check and cannot be verified in bulk.

## Rejection reasons

A change is rejected on sight when it carries one of these. The list is the failure set
the gates below are built against; it is not exhaustive, and a maintainer may reject a
change that fails the bar for a reason it does not name.

1. **Not understood.** The responsible human cannot explain the change line by line. This
   is the bar; everything below is a shape that usually means the bar was missed.
2. **An unread field.** A field, knob, string, or endpoint nothing reads, or a reader that
   is not the one the prose names. One reader per field.
3. **A claim the code does not hold.** A docstring that restates the function name, a
   comment narrating the next line, docs describing behavior the code does not implement.
4. **A test without an assertion,** or a fallback for a case that cannot occur.
5. **Generated-code tells.** `Note:`/`Important:` filler, repeated boilerplate headers,
   marketing adjectives about our own code, decorative separators, emoji, stacked "X, not
   Y" rhetoric, symmetrical comment blocks around trivial code. The rule and its counter
   are in the project's writing-quality rules and `scripts/prose_tells.py`.
6. **A silent default.** An engine, telemetry path, or network call that starts without an
   explicit opt-in, or a fix that falls back silently where the product contract says fail
   closed.
7. **Prose that restates the diff.** A description that narrates what the code already
   says, instead of naming the reason — the constraint, the number, the bug being guarded.

## CI

The gates below run on every push to `main`/`develop` and every pull request into `main`.
This is what the disclosure and rejection rules rest on — a rule nobody measures stays a
wish.

| Gate | Rule it holds | Where |
|---|---|---|
| Hand-written prose (`prose_tells.py --strict`) | Rejection 3 and 5: generated-code tells in comments and docstrings, counted per file against a baseline that only ever lowers | `ci-gates.yml` |
| English-only (`language_gate.py`) | Every developer and machine-facing artifact is English; German exists only in the product's own locale | `ci-gates.yml` |
| Architecture wall (`architecture_check.mjs`) | The 400-line ceiling, import cycles, and the contracts the tree pins | `ci-gates.yml` |
| Author register (`attribution_check.py`) | Every new commit's author address is one the register accepts; history stays as the clean-room decision wrote it | `hygiene.yml` |
| Repository hygiene | No tracked `node_modules`, local databases, WAL/SHM, secrets, caches, or generated artifacts; no case-collision paths | `hygiene.yml` |
| Workflow self-audit (zizmor) | Every workflow file, under its strictest reading | `ci-gates.yml` |
| Lint and types (ruff blocking subset, mypy advisory) | `scripts/lint_policy.sh` | `lint.yml` |
| Secret scan | No credential enters the tree | `secret-scan.yml` |

Two limits, stated because a green tree is not a certificate:

- The prose gate counts comment and docstring markers under the shipped roots. It does not
  read every string literal, so a file can pass the gate and still carry a tell a reader
  sees. Green means "no counted tell", not "understood".
- Pull requests from a fork do not run these gates: they execute on a self-hosted runner,
  and running a fork's code there is not acceptable. A maintainer reviews a fork PR by
  hand and can run the gates on request.

## Enforcement

CI is necessary, not sufficient. Rejection 1 — the change the responsible human cannot
explain — has no script, and is the reviewer's call. The gates remove the mechanical
excuses so that the review is spent on the reasoning, which is the part automation cannot
certify.
